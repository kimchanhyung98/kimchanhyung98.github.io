## 이영재

### spring.jpa.hibernate.ddl-auto: update << 어떻게 하는게 좋을지(제거 or 유지)

Spring Boot 프로젝트에서 `spring.jpa.hibernate.ddl-auto` 설정값을 어떻게 사용하는 것이 가장 좋을까요?
특히 대학생 토이 프로젝트에서 이 설정을 계속 사용해도 될지, 아니면 개발 단계에 따라 변경해야 할지 궁금합니다.

- 토이 프로젝트 개발 시: `update` 사용 (편의성, 데이터 유지)
- 실서비스 또는 학습 목적: `validate` 또는 `none` + 스키마 마이그레이션 도구 (**Flyway**, **Liquibase**) 권장
- 주요 옵션:
    - `create`: 기존 테이블 삭제 후 재생성 (초기 데이터 로드 가능)
    - `create-drop`: `create`와 유사, 앱 종료 시 테이블 삭제 (테스트용)
    - `update`: 기존 스키마에 변경사항 반영 시도 (일부 DDL 미지원)
    - `validate`: 엔티티-DB 스키마 일치 여부 검증
    - `none`: DDL 작업 안 함
- 학습 포인트: `ddl-auto` 한계점 및 마이그레이션 도구 필요성 인지

### 깃에 푸시할때 주석, 프로그램 로그찍는 코드를 놔두는것이 나쁜지(ex: ocr 인식 결과)

코드에 개인적인 메모나 임시 생각, 또는 OCR 인식 결과 화면 출력과 같은 디버깅용 로그 코드를 그대로 남겨둔 채
팀원들과 공유하는 Git 저장소에 커밋하고 푸시해도 괜찮을까요? 이것이 나쁜 개발 습관인지 궁금합니다.

- 커밋 전 정리: 불필요한 디버깅 코드, 임시 주석은 메인 브랜치 병합 전 제거
- 로깅: **SLF4J**와 **Logback/Log4j2** 등 로깅 프레임워크 사용, 로그 레벨 설정으로 관리
    - 상세 로그(예: OCR 결과)는 DEBUG/TRACE 레벨로, 운영 환경은 INFO 이상
- 커밋 메시지: 변경 내용과 이유를 명확히, 표준 규칙 준수
- 중요성: 코드 가독성, 유지보수성, 협업 효율 향상

### 만약 퀴즈기능을 gpt 안쓰고 한다면 어떻게 하면 좋을지(향후 계획)

GPT와 같은 AI를 사용하지 않고 퀴즈 기능을 구현해야 한다면, 특히 향후 기능 확장을 고려했을 때, 문제 생성, 관리, 채점 로직을 어떤 방식으로 설계하고 개발해야 할까요?

- DB 설계: `Users`, `Quizzes`, `Questions` (유형, 난이도, 점수 포함), `Answers` (정답 포함), `UserQuizAttempts` (성적) 등 테이블 구성
- 문제 생성: 관리자용 문제/정답 입력 기능 (수동)
- 퀴즈 로직: 문제 제시, 답안 입력, 채점 및 결과 저장 로직 구현
- 확장 방안: 문제/보기 섞기, 피드백 제공, 난이도별 출제, 문제 태그화

## 이재준

### 기능 작동 여부 관련 테스트가 아니라 데이터베이스 적용 여부를 확인하는 테스트는 어떻게 하면 좋은지 궁금합니다.

단순히 프로그램 코드의 기능 실행 여부만이 아니라, 로직에 따라 데이터가 데이터베이스에 정확하게 저장, 수정, 삭제되었는지 검증하는 테스트는 어떻게 구성해야 할까요?

- 핵심: DB 작업 후, 상태가 예상과 일치하는지 **단언(assert)**
- Spring Boot: **`@DataJpaTest`** 활용
    - 리포지토리 계층 테스트, 관련 빈만 로드
    - 기본 인메모리 DB (H2) 사용, 테스트 후 롤백
    - DB 작업 후 `findById()`, `findAll()` 등으로 상태 확인 및 검증
- 테스트 환경:
    - H2 DB: 간편, 빠름 (운영 DB와 100% 동일 X)
    - **Testcontainers**: Docker로 실제 DB 환경과 유사하게 테스트 (신뢰도 향상)
- 검증 항목: 필드 값, 관계, 제약 조건 등

### 테스트 코드를 작성할 때 테스트 유닛을 만들어서 하는 것이 좋은지 (스프링 부트 테스트), 비즈니스 로직에 임시 코드를 놓는 것이 좋은지 궁금합니다.

비즈니스 로직 테스트 코드 작성 시, 별도의 전용 테스트 파일(JUnit, Spring Boot Test 등 활용)을 구성하는 것과
임시 테스트 코드를 비즈니스 로직 코드 내에 직접 포함하는 방식 중 어느 것이 더 바람직한가요?

- 정석: 전용 테스트 파일 사용 (`src/test/java`)
    - 장점: 관심사 분리, 유지보수 용이, 명확성, 빌드/테스트 프레임워크 호환
- 비즈니스 로직 내 임시 코드: 비권장 (코드 복잡도 증가, 가독성 저하, 배포 위험)
- Spring Boot 표준: `src/main/java`와 동일 구조로 `src/test/java`에 테스트 클래스 작성

### 기능 테스트를 할 때 혼자서 하는 것은 한계가 있는 것 같은데 어떻게 하는 것이 좋은지 궁금합니다.

혼자 또는 소규모 팀으로 기능 테스트를 진행할 때, QA 팀 부재나 다양한 관점 부족으로 인한 한계를 인지하면서도 이 과정을 어떻게 더 효과적이고 관리 가능하게 만들 수 있을까요?

- 명확한 요구사항/완료 기준 정의
- 중요/고위험 기능 우선 테스트
- 단위/통합 테스트로 기본 품질 확보
- **탐색적 테스트**로 예상 못한 버그 발견
- 주요 사용자 시나리오 기반 테스트
- 다양한 테스트 데이터 활용 (경계값, 예외값 등)
- (선택) 반복 작업은 간단한 자동화 고려

### api를 만들 때 기능을 어느정도 통합하여 (책임과 분리는 명확하게하되) 만드는 것이 좋은지, 기능 하나하나 다 만드는 것이 좋은지 궁금합니다.

API 설계 시, 하나의 엔드포인트가 처리해야 할 기능의 범위를 어떻게 정해야 할까요? 관련된 여러 작업을 묶어 더 큰 API로 구성해야 할지,
아니면 각기 고유 기능을 수행하는 작은 API들을 다수 만들어야 할지, 책임과 역할을 명확히 분리하면서 이 균형을 어떻게 맞출 수 있을까요?

- 핵심 원칙: 높은 **응집도(Cohesion)**, 낮은 **결합도(Coupling)**
- 설계: **리소스 중심 설계 (RESTful)** - 예: `/quizzes`, `/users`
    - HTTP 메소드(GET, POST, PUT, DELETE)로 작업 정의
- 고려 사항: 사용 사례, 원자성/트랜잭션, 유지보수성, 복잡도
- 토이 프로젝트: 리소스 중심으로 시작, 각 API는 명확한 책임 부여. 극단적 분리/통합 지양

## 유성진

### 만들어진 api들에 대해 최적화(성능, 보안, 메모리 등)를 하려면 어떻게 해야하는지

개발 중인 API의 성능(응답 속도, 처리량), 보안(일반적인 웹 취약점 방어), 메모리 사용량(특히 Spring Boot 환경)을 개선하기 위해 알아야 할
기본적인 전략이나 좋은 습관, 그리고 직접 적용해볼 만한 방법들은 무엇일까요?

- **1. 성능:**
    - 캐싱: **Spring Cache**, HTTP 캐싱 (자주 쓰는 데이터 DB 접근 최소화)
    - DB 쿼리: 효율적 쿼리, **인덱싱**, N+1 문제 방지
    - 비동기 처리: **`@Async`** 등으로 오래 걸리는 작업은 백그라운드 실행
    - 페이로드: 응답 압축(Gzip), 페이지네이션
    - 커넥션 풀: DB 커넥션 풀 (HikariCP) 효율적 사용
- **2. 보안:**
    - 입력값 검증: **Spring Validation** (SQL 인젝션, XSS 방지)
    - 인증/인가: **Spring Security** (안전한 인증, 역할 기반 접근 제어)
    - HTTPS 사용: 데이터 전송 암호화
    - 민감 정보 노출 최소화: 일반적 에러 메시지 사용
    - **OWASP API Security Top 10** 기본 사항 숙지
- **3. 메모리 (Java/Spring Boot):**
    - 효율적 객체 사용: 불필요한 객체 생성 자제, 적절한 컬렉션 활용
    - 리소스 관리: `try-with-resources`로 외부 리소스 해제 (메모리 누수 방지)
    - Spring 빈 스코프 이해, 필요시 지연 초기화 사용
    - JVM 힙 설정(`-Xms`, `-Xmx`), GC 기본 원리 이해
    - 불필요한 의존성 제거

### 전체 흐름도(플로우차트), 기능 흐름도 등을 어떻게 작성하면 좋을지, 회사에서는 어떻게 작성하는지

프로젝트의 전체 시스템 흐름이나 특정 기능의 처리 과정을 효과적으로 시각화하는 다이어그램(시스템 흐름도, 기능 흐름도 등)을 어떻게 작성해야 할까요?
또한, 실제 회사에서는 이러한 다이어그램을 계획, 소통, 문서화 목적으로 어떻게 활용하는지 궁금합니다.

- 종류:
    - 프로세스 순서도/워크플로우: 기능의 단계별 처리 흐름 시각화
    - 시스템 아키텍처 다이어그램: 주요 구성요소(FE, BE, DB)와 상호작용 표현
    - 데이터 흐름 다이어그램 (DFD): 시스템 내 데이터 이동/변환 과정
- 작성 팁:
    - 목적 명확화, 표준 기호 사용, 단순/간결하게 표현
    - 논리적 흐름, 일관된 스타일 유지
    - 검토 및 피드백 통해 개선
- 활용 (회사): 계획/설계, 커뮤니케이션/협업, 문서화, 분석/개선
- 도구: **draw.io (diagrams.net)**, Lucidchart, Miro (손그림도 초기 구상에 유용)
