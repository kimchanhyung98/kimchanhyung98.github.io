## 이영재

### spring.jpa.hibernate.ddl-auto: update << 어떻게 하는게 좋을지(제거 or 유지)

`spring.jpa.hibernate.ddl-auto`를 어떻게 설정하는 것이 좋을까요?

- `hibernate.ddl-auto` : 엔티티 코드를 변경하면 데이터베이스 테이블도 자동으로 변경
- 토이 프로젝트이니 `update`를 사용하고, 실서비스라면 (특히 중요한 데이터가 있다면) `validate` 옵션을 사용
    - 별도의 마이그레이션 도구를 사용해서 변경 이력을 추적하고 관리하는 것을 권장 (IaC 관점?)

### 깃에 푸시할때 주석, 프로그램 로그찍는 코드를 놔두는것이 나쁜지(ex: ocr 인식 결과)

개인적인 메모나 주석이나 함수 실행 결과 같은 디버그 로그를 그대로 남겨둔 채, 커밋해도 괜찮을까요?

- 어디에 커밋(혹은 병합)하는지를 고려
    - 개인(feature) 브랜치라면 자유롭게 커밋 (아이디어 메모, 슈도코드, 임시 주석, 디버그 로그 등). 진행 상황이나 고려 대상을 확인하기에 용이함
    - 메인(main, develop) 브랜치라면 리뷰하고 불필요한 내용은 정리(제거)
- 로그 레벨(error, warning, info, debug 등) 활용
    - 시스템에 영향을 주는 로그와 확인을 위한 단순 로그는 구별하여 관리
- 문서화 및 주석 활용 (`// TODO : msg...` , `// FIXME : msg...` , `// XXX : msg...` 등)
    - (단순한 코드가 아니라면) 복잡한 로직, 결정의 배경(왜 이렇게 구현했는지), 또는 외부 시스템과의 연동 등을 설명

### 만약 퀴즈기능을 gpt 안쓰고 한다면 어떻게 하면 좋을지(향후 계획)

AI를 사용하지 않고 퀴즈 기능을 구현해야 한다면, 문제 생성, 관리 로직을 어떤 방식으로 개발해야 할까요? (향후 기능 확장도 고려)

- 문제 은행 방식. 키워드나 태그를 추출하고, 난이도별 알고리즘을 적용하여, 미리 저장해둔 문제와 답을 제공
- 현실적인 접근
    - 'AI를 안 쓰고 한다면'이라는 가정 자체가 오류
    - 옛날부터 IDE 사용법이나 개발 도구 활용법이 중요했던 것처럼, 미래에는 AI를 얼마나 잘 이해하고 활용하는지도 중요한 역량이 될 것
    - 'AI를 활용해서 어떻게 개선할 수 있을까?' 나 'AI 퀴즈 생성의 퀄리티를 어떻게 높일 수 있을까?' 같은 활용 방안을 고민

## 이재준

### 기능 작동 여부 관련 테스트가 아니라 데이터베이스 적용 여부를 확인하는 테스트는 어떻게 하면 좋은지 궁금합니다.

기능 실행 여부만이 아니라, 데이터가 데이터베이스에 정확하게 저장, 수정, 삭제되었는지 검증하는 테스트는 어떻게 해야 할까요?

- 테스트 유형 확인
    - 단위 테스트 (Unit Test) : 개별 함수나 메소드의 로직 검증 (Mock)
    - 통합 테스트 (Integration Test) : 여러 컴포넌트나 모듈들이 같이 잘 동작하는지, 서비스 계층의 로직 검증 (DB와의 연동 검증)
    - 기능 테스트 (Feature Test) / 종단간 테스트 (End-to-End Test) : 사용자 관점에서 전체 기능 흐름 검증
        - 회원 가입 기능을 테스트한다면, Request부터 시작해서 서비스 로직, DB에 유저 정보가 정상적으로 저장되었는지까지 확인
- 현실
    - 자원(시간, 인력, 비용)이 한정적임. 테스트가 누락되거나, Feature Test만 진행하거나, Feature&Unit Test만 진행

### 테스트 코드를 작성할 때 테스트 유닛을 만들어서 하는 것이 좋은지 (스프링 부트 테스트), 비즈니스 로직에 임시 코드를 놓는 것이 좋은지 궁금합니다.

테스트 코드 작성 시, 별도의 테스트 파일(JUnit, Spring Boot Test 등 활용)을 구성하는 것과
비즈니스 로직 내에 임시 테스트 코드를 포함하는 방식 중, 어느 것이 더 좋을까요?

- 테스트 코드는 반드시 실제 로직과 분리하여 작성
    - 목적/책임 분리, 유지보수, 가독성, 안정성 등
- 만약, 임시 테스트 코드가 있다면 로컬에서 개인적으로 확인&사용 후, 반드시 제거하거나 분리

### 기능 테스트를 할 때 혼자서 하는 것은 한계가 있는 것 같은데 어떻게 하는 것이 좋은지 궁금합니다.

혼자 기능 테스트를 작성&진행할 때, 자원(시간, 인력, 기획 이해도) 부족으로 인한 한계가 있는데, 어떻게 작업하거나 관리하는게 좋을까요?

- 우선순위 결정
    - 현실적으로 모든 코드와 기능을 테스트할 수는 없음. 프로젝트의 핵심 기능이나 사용자가 자주 사용하는 기능, 오류 발생 시 가장 치명적인 부분부터 테스트
    - 프로젝트 기획 시, 각 기능의 중요도와 구현 우선순위를 결정하여 MVP(Minimum Viable Product)를 정의하고 동작 확인 (기획 이해도가 중요)
- 문서화 및 시간 관리
    - 개발과 테스트를 혼자 하다보면, 한 가지나 특정 로직에 매몰되어 작업 시간이 지연될 수 있음
    - AI를 활용한 서비스를 개발하는데, 테스트에도 AI 활용

### api를 만들 때 기능을 어느정도 통합하여 (책임과 분리는 명확하게하되) 만드는 것이 좋은지, 기능 하나하나 다 만드는 것이 좋은지 궁금합니다.

API 설계 시, 하나의 엔드포인트가 처리해야 할 기능의 범위를 어떻게 정해야 할까요.
여러 기능을 통합하여 구성해야 할까요, 따로 만들어야 할까요?

- 기본 고려 사항은 단일 책임 원칙 (SRP). 각 API 엔드포인트는 하나의 주된 기능 또는 명확한 책임을 갖도록 설계
    - 너무 작게 쪼개면 : 클라이언트가 API를 여러 번 호출해서 비효율 (Chatty API)
    - 너무 크게 묶으면 : API가 복잡해지고, 불필요한 정보까지 요청하고, 영향 범위가 커짐
- 개인적인 의견
    - RESTful API 설계 가이드 확인. ~~설계는 정답이 있기보다는, 요구사항, 자원, 환경, 확장 등을 고려해서 적당하게 해야함~~
    - 리소스(혹은 도메인) 중심으로 시작 : 대상을 중심으로 API를 구성하고, 각 대상에 필요한 CRUD(생성, 조회, 수정, 삭제) 작업을 정의
    - 확장성(Expandability) 고려 : 응답 형식을 유연하게 하거나, 선택적으로 정보를 제공하는 옵션 등
    - 마이크로서비스처럼 명확한 기능적 경계(Bounded Context)를 설정. (이 기능이 완전히 독립된 작은 서버나 서비스로 존재한다면 어떨까?)

## 유성진

### 만들어진 api들에 대해 최적화(성능, 보안, 메모리 등)를 하려면 어떻게 해야하는지

API의 성능(응답 속도, 처리량)이나 보안(일반적인 취약점 방어)을 개선하려면 어떻게 해야될까요?

- 최적화 사유부터 고민 : 사용자 경험, 보안 사고, 운영 비용 등
    - 성능 최적화 : 캐싱, DB 쿼리 최적화&인덱싱, 비동기 처리, 압축 등
    - 보안 최적화 : 입력값 검증, 인증 및 권한 개선, 오류 처리, 주요 취약점 이해, 보안 업데이트 및 패치 등
- 서비스에 기능이 추가되고, 사용량이 늘어남에 따라 새로운 병목 지점이 나타날 수 있음. 최적화는 지속적으로 진행

### 전체 흐름도(플로우차트), 기능 흐름도 등을 어떻게 작성하면 좋을지, 회사에서는 어떻게 작성하는지

프로젝트의 시스템 플로우나 특정 기능의 처리 과정을 시각화하는 다이어그램을 어떻게 작성해야 할까요?
회사에서는 이러한 다이어그램을 계획, 소통, 문서화 목적으로 어떻게 작성하고 활용하는지 궁금합니다.

- 어떤 작업을 하는지?
    - 해당 기능의 단계별 처리 흐름 시각화하기 위해, 프로세스 순서도/워크플로우
    - 주요 구성요소(FE, BE, DB)와 상호작용 표현하기 위해, 시스템 아키텍처 다이어그램
    - 시스템 내 정보 이동/변환 과정을 알기 위해, 데이터 흐름 다이어그램 (DFD)
- 목적 명확화, 단순/간결하게 표현, 논리적 흐름, 일관된 스타일 유지
    - draw.io 나 Mermaid 등 도구 활용
